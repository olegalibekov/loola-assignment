# loola-harness

Из однофайлового цикла с одним инструментом `bash` ([baseline/agent_original.py](baseline/agent_original.py))
сделан небольшой харнесс с двумя механизмами из задания:

1. **Динамическая подгрузка тулов и скиллов**: 39 инструментов и 10 скиллов, но в каждом запросе модель
   видит только 7 схем и короткий индекс.
2. **Context compaction**: при заполнении окна старая часть диалога заменяется структурированным саммари.

Оба механизма спроектированы так, чтобы **не ломать prompt cache** (KV-cache префикса). Это проверяется
тестами и измеряется метрикой `prefix_reuse`.

> **Статус измерений.** Механика измерена офлайн-реплеем (без модели). На реальной модели
> (`gemini-3.5-flash-lite`) выполнено **по одному-два прогона на вариант**: это предварительные цифры, а не
> статистика. Серия из пяти прогонов на вариант не завершена: ключ пропускает около 16 запросов в минуту.
> Таблицы ниже сохраняют результаты версии до исправлений песочницы и обработки ошибок. После этих
> исправлений проверены тесты и Docker selfcheck. Новые попытки реальных прогонов встречали HTTP 503 и 429;
> сопоставимая серия для текущей версии пока не завершена.

## Быстрый старт

```bash
python -m venv .venv && .venv/bin/pip install -e ".[dev]"
cp .env.example .env            # LLM_BASE_URL, LLM_API_KEY, LLM_MODEL (любой OpenAI-совместимый эндпоинт)

.venv/bin/python -m pytest                       # тесты без сети и без модели
.venv/bin/python -m bench.replay                 # офлайн-замер механики
.venv/bin/python -m bench.run --runs 5           # до/после на реальной модели
.venv/bin/python -m bench.sandbox                # собрать образ и проверить, что ключ недоступен агенту
.venv/bin/python -m bench.run --docker --runs 5  # то же в Docker-песочнице
.venv/bin/python -m harness "почини тесты" --workdir ./project
```

Для ограничения расходов: `--max-api-attempts 100 --max-wall-seconds 600` у `harness` или `bench.run`.
Те же параметры доступны через `MAX_API_ATTEMPTS` и `MAX_WALL_SECONDS`; `0` отключает лимит.
Счётчик включает HTTP-повторы и запросы на саммари; итоговые статусы — `request_limit` и `time_limit`.
Лимит времени кооперативный: проверяется между операциями и ограничивает ожидание HTTP, но не прерывает
уже выполняющийся файловый инструмент или сервер, непрерывно передающий ответ. У бенчмарка дополнительно
есть внешний `--timeout`; исходный baseline использует только его. `Ctrl+C` сохраняет статус
`interrupted` и метрики. Некорректные размеры окна и лимиты отклоняются до запуска.

### 1. Динамическая подгрузка

Три режима (`--tool-mode`), чтобы сравнивать их между собой:

| Режим | Что в `tools` | Цена |
|---|---|---|
| `eager` | Все 39 схем сразу, тела всех скиллов в системном промпте | ~6 000 токенов в каждом запросе |
| `append` | Схема добавляется в `tools` после `tool_search` | Каждая подгрузка меняет начало промпта и сбрасывает кеш |
| `dispatch` (по умолчанию) | Всегда одни и те же 7 схем | ~1 700 токенов, префикс не меняется никогда |

В режиме `dispatch`:

- В `tools` постоянно лежат `bash`, `read_file`, `write_file`, `edit_file`, `tool_search`, `use_tool`, `load_skill`.
- В системном промпте есть **статический индекс каталога в виде сигнатур**: `grep(pattern, path?, include?, ...)`.
  Это ~10% от размера полных схем, и этого обычно хватает, чтобы вызвать инструмент без лишнего запроса.
- Инструмент каталога вызывается через `use_tool(name, arguments)`. Харнесс валидирует аргументы по схеме.
- Полная схема приходит **результатом тула** (`tool_search`), то есть в хвост контекста. Ошибка валидации
  тоже содержит схему, так что модель исправляется за один шаг.
- Скиллы: в промпте только строка «имя: описание». Тело приходит результатом `load_skill`. Повторная загрузка
  того же скилла возвращает короткую отсылку, пока тело ещё в контексте.
- У каждой строки индекса есть триггер «когда загружать» (например, «Load before opening any log file»).
- Правила процесса (сверить каждое требование с фактическим состоянием, зелёные тесты не доказательство)
  лежат в постоянном промпте, а не в скиллах: модели редко загружают скиллы сами (см. результаты).
- Скиллы не содержат подсказок к задаче бенчмарка. Это проверяет тест
  `test_skills_do_not_leak_task_specifics`: первая версия скиллов такие подсказки содержала, прогоны с ней
  отброшены.

### 2. Compaction

- **Вывод тулов ограничивается на входе** (8 000 символов: начало и конец, полученный текст сохраняется
  в файл, путь указан в маркере). При захвате subprocess каждый поток дополнительно ограничен 1 МиБ:
  сохраняются начало и конец, пропущенный объём указан явно. Для полного большого вывода команда должна
  перенаправить его в файл. Поэтому историю не приходится переписывать из-за одного `cat`.
- **Триггер**: оценка промпта превысила 75% полезного окна (окно минус резерв на ответ). Оценка токенов
  калибруется по реальному `usage.prompt_tokens` сервера.
- **Разрез** идёт по границе хода, вызов тула никогда не отделяется от результата. Хвост (до 25% окна)
  остаётся дословно.
- **Уровень 1, без вызова модели**: старые большие выводы тулов заменяются детерминированной заглушкой
  (размер, первая и последняя строка). Сообщения ассистента не меняются, тела скиллов сохраняются.
  Применяется, только если этого хватает, чтобы опуститься ниже 50% окна.
- **Уровень 2, саммари**: иначе модель пишет записку по фиксированной структуре: Done / Files / Key facts /
  Problems / Unverified / Next. Какой уровень сработает, решается до любых правок истории, поэтому запрос на
  саммари всегда равен уже отправленному префиксу плюс одно сообщение и попадает в кеш.
- **Непроверенные требования не теряются.** Раздел Unverified перечисляет то, что не сделано или не сверено
  с задачей; блок саммари требует закрыть его до финального ответа. Если следующее саммари раздел потеряло,
  харнесс дословно переносит предыдущий.
- **Состояние харнесса** (загруженные скиллы, найденные инструменты, каталог с полными выводами) дописывается
  в саммари детерминированно, а не доверяется модели.
- **Результат уровня 2**: `[system, user(задача + саммари), хвост]`. Системный промпт и текст задачи остаются
  байт-в-байт прежними.
- **Отказоустойчивость**: если сервер вернул ошибку переполнения, харнесс сжимает контекст и повторяет запрос;
  если не помогло, сжимает без хвоста. Если саммари получить не удалось, подставляется механический лог вызовов.

### 3. Что ещё исправлено в исходном коде

| Проблема в исходнике | Что сделано |
|---|---|
| На каждый tool call добавлялось отдельное assistant-сообщение (невалидная история при параллельных вызовах) | Одно assistant-сообщение со всеми вызовами, затем по одному `tool` на вызов |
| `json.loads` аргументов без защиты ронял цикл | Очевидные случаи чинятся (markdown-ограждение, двойное кодирование), остальное возвращается модели как `ERROR [invalid_json]` |
| Нет таймаута и ретраев HTTP, `raise_for_status` убивал прогон на 429/5xx | Ретраи с backoff и `Retry-After`; 401/403/404 завершают прогон сразу |
| `finish_reason` игнорировался | Обрезанный tool call не исполняется; `content_filter` и неизвестные причины остановки не считаются успехом и не запускают тулы |
| Вывод тула не ограничен | Ограниченный захват subprocess и отдельный лимит текста в промпте; сохранение захваченного текста в файл |
| Таймаут `bash` не убивал дочерние процессы, stdin был открыт | Своя группа процессов и `killpg`, ограниченное ожидание закрытия pipe даже при сбежавшем потомке, stdin закрыт |
| `usage` выбрасывался | Метрики и JSONL-трейс по каждому запросу и вызову |
| Ключ и URL в коде | Конфигурация из окружения или `.env` |
| Модель могла зациклиться на одном вызове до `MAX_TURNS=1000` | Предупреждение на 3-м одинаковом вызове подряд, остановка на 6-м |
| `temperature=0.1` зашита в код | Настраивается, `LLM_TEMPERATURE=none` убирает параметр (часть моделей отклоняет нестандартные значения) |
| Служебные поля провайдера в ответе терялись бы при пересборке истории | Поля вызова тула и `reasoning_details` / `extra_content` сообщения возвращаются без изменений (Gemini требует thought signature, иначе 400) |
| Ключ API наследовался командами агента (`env` его показывал) | Из окружения команд убраны `LLM_*` и всё похожее на секрет; полная изоляция есть в Docker-песочнице |
| Сообщение о таймауте не говорило о побочных эффектах | Модель предупреждается, что убитая команда могла успеть изменить файлы |

## Песочница

Агент исполняет произвольные команды. В Docker ([Dockerfile](Dockerfile), [bench/sandbox/docker.py](bench/sandbox/docker.py)):

- Харнесс работает от root и единственный держит ключ API, причём только в своём окружении: файла `.env` нет
  ни в образе, ни в монтированиях.
- Команды модели исполняются от непривилегированного пользователя с очищенным окружением. Чужой
  `/proc/<pid>/environ` ему недоступен.
- Харнесс сохраняет capability `KILL`, чтобы таймаут мог остановить группу процессов другого UID.
- Для `original` и `original-retry` это обеспечивает отдельный
  [launcher](bench/sandbox/baseline.py): исходный скрипт и поведение его цикла не меняются.
  Docker-бенчмарк нужно запускать от обычного пользователя хоста; UID 0 отклоняется.
- Файловые инструменты, которые работают внутри процесса харнесса, ограничены рабочим каталогом и каталогом
  прогона. Иначе ключ читался бы через `read_file /proc/self/environ`.
- Рекурсивный поиск пропускает ссылки за пределы разрешённых каталогов; рекурсивное копирование и создание
  архивов в песочнице отклоняют вложенные символические ссылки. Распаковка ZIP/tar принимает только обычные
  файлы и каталоги и проверяет пути. SQLite `ATTACH` и `VACUUM INTO` в песочнице отключены.
- Монтируются только рабочий каталог прогона и каталог с трейсами. Репозиторий не монтируется.
- Чекер запускается во втором контейнере без сети и без ключа: он исполняет код, написанный агентом.
  Это отдельный образ с суффиксом `-checker`; в образе агента нет чекера, генератора задачи или
  эталонного решения из `bench/runners/replay.py`.

`python -m bench.sandbox` собирает два образа и выполняет 20 проверок доступа и работоспособности (через `bash`,
`/proc`, вложенные ссылки, файловые тулы, `env_get`, дочерний Python, baseline launcher, таймаут и отсутствие
эталонного решения в образе агента). Все 20 проверок прошли с тестовым ключом. Отдельный образ чекера
проверен на заскриптованном эталонном решении: 12/12. Это проверка конвейера, не результат работы модели.
Конвейер бенчмарка в Docker также проверен на мок-модели; на реальной модели в контейнере прогонов ещё не было.

Чего песочница не даёт: у контейнера агента есть сеть (харнессу нужен эндпоинт модели), так что команды
модели тоже могут ходить в сеть.

## Бенчмарк

**Задача** ([bench/task/workspace.py](bench/task/workspace.py)): сгенерированный по сиду Python-проект. Девять шагов:
найти единственную FATAL-запись в логе на 3 000 строк (290 КБ) среди сотни ложных `incident=`, починить баги
в трёх модулях, реализовать функцию и CLI-команду, посчитать агрегаты по CSV на 1 500 строк с «грязными»
полями, написать тесты, changelog, отчёт и закоммитить. В последнем шаге нужен идентификатор из первого:
это проверка того, что compaction не теряет факты.

**Чекер** ([bench/task/check.py](bench/task/check.py)): 12 независимых проверок, успех только при 12/12. Эталонные значения
пересчитываются из данных, заново сгенерированных по сиду. Скрытые тесты запускаются против пакета агента,
поэтому правка видимых тестов не помогает. Нетронутый проект проходит 0/12, эталонное решение 12/12
(проверяется в [tests/bench/task/test_bench.py](tests/bench/task/test_bench.py)).

### Офлайн-реплей (без модели)

`python -m bench.replay` прогоняет **одну и ту же** заскриптованную траекторию через каждый вариант харнесса.
Траектория намеренно неэкономная: читает файлы целиком, запускает тесты в verbose. Тулы исполняются
по-настоящему, чекер проверяет результат. Токены оцениваются как символы/4.

Что это показывает: сколько промпта несёт каждый запрос, какая его доля является повторяемым префиксом,
переживает ли прогон маленькое окно. Что это **не** показывает: справится ли реальная модель.

Результаты из [bench/results/replay-offline.md](bench/results/replay-offline.md):

| Окно | Вариант | Итог | Проверки | Запросов | Prompt-токены | Повторяемый префикс | Некешируемый prompt | Сжатий |
|---|---|---|---|---|---|---|---|---|
| без лимита | eager, без обрезки и сжатия (**до**) | finished | 12/12 | 49 | 806 127 | 97% | 23 577 | 0 |
| без лимита | append | finished | 12/12 | 65 | 825 697 | 87% | 110 937 | 0 |
| без лимита | dispatch (**после**) | finished | 12/12 | 56 | 670 927 | 97% | 19 847 | 0 |
| 24 000 | eager, без обрезки и сжатия (**до**) | context_overflow | 11/12 | 45 | 712 367 | 97% | 21 974 | 0 |
| 24 000 | dispatch (**после**) | finished | 12/12 | 57 | 551 567 | 95% | 25 170 | 1 |
| 12 000 | eager, без обрезки и сжатия (**до**) | context_overflow | 0/12 | 5 | 34 643 | 79% | 7 359 | 0 |
| 12 000 | eager + обрезка + сжатие | finished | 12/12 | 64 | 523 712 | 91% | 46 995 | 15 |
| 12 000 | dispatch (**после**) | finished | 12/12 | 60 | 353 170 | 92% | 27 051 | 4 |

Выводы:

- **Постоянная часть промпта**: 5 855 токенов в `eager` против 1 919 в `dispatch` (−67%).
- **Без лимита окна** суммарный prompt падает на 17% (806 тыс. → 671 тыс.), хотя запросов больше (56 против 49):
  подгрузка скилла стоит отдельного запроса.
- **Подгрузка не бесплатна.** Если модель перед каждым первым вызовом запрашивает полную схему, выигрыш
  исчезает (831 тыс., строка «schema lookups» в полном отчёте). Поэтому сигнатуры лежат в статическом промпте.
- **`append` против `dispatch`**: при той же траектории некешируемый prompt в 5 раз больше (111 тыс. против
  22 тыс.), потому что каждая подгрузка схемы сдвигает начало промпта.
- **Маленькое окно**: «до» падает с переполнением (после 45 запросов при 24 тыс. и после 5 при 12 тыс.), «после»
  завершает задачу 12/12.
- **Одного compaction мало.** При окне 12 тыс. вариант `eager` со сжатием выживает, но сжимается 15 раз:
  статическая часть занимает больше половины окна. С `dispatch` хватает 4 сжатий.
- **Уровень 1 в реплее не сработал ни разу.** Основной объём этой траектории лежит в аргументах вызовов
  (содержимое файлов), а их уровень 1 намеренно не трогает.

### Реальная модель: предварительно, один-два прогона на вариант

`gemini-3.5-flash-lite` через OpenAI-совместимый эндпоинт Google, `temperature=0.1`, резерв ответа 4 096.
**N=1 без лимита окна и N=2 под окном 16k**, поэтому это показания, а не измерение. Исходные файлы:
[без лимита](bench/results/20261125-161442-quick-unlimited.md),
[окно 16k, первый прогон](bench/results/20261125-162042-quick-16k.md),
[окно 16k, второй прогон](bench/results/20261125-164319-16k-second.md),

Что видно и чего не видно:

- **Экономии токенов без лимита окна в этой паре нет.** Новый харнесс потратил на 11% больше prompt-токенов,
  чем `eager`, и его пик выше. Оба прошли 12/12. При одном прогоне это шум: более ранний прогон того же
  варианта (до правок скиллов, поэтому в таблицу не включён) занял 241 тыс. токенов и 29 ходов.
- **Кеш работает в обоих вариантах** (74% и 79% prompt-токенов из кеша), поэтому постоянная часть `eager`
  почти ничего не стоит. Главная ценность ленивой подгрузки здесь занятость окна, а не деньги.
- **Под окном 16k compaction решает исход: 2 из 2 против 0 из 2.** Без сжатия оба прогона переполнили окно
  (на 32-м и 26-м ходу) и остановились с 10/12 и 6/12. Со сжатием оба завершились 12/12, по три саммари
  в каждом, пик промпта 8,8 тыс. токенов.
- **Факт из первого шага пережил три сжатия** в обоих прогонах: идентификатор инцидента в `REPORT.md` верный.
- **Уровень 1 не сработал ни разу** (0 из 6 сжатий), как и в реплее.
- **Цена сжатия для кеша**: доля кеша 43–44% против 52–60% без сжатия.
- **Скиллы модель загружает редко**: 2 загрузки за прогон без лимита, 4–6 под окном 16k. В `eager` модель
  сделала 20 вызовов инструментов каталога, в `full` без лимита ни одного: обошлась базовыми.
- **Точки «до» для исходного скрипта нет.** Во всех пяти попытках он падал на первом же 503 от сервера
  (на 1–4-м запросе), потому что не делает повторов. Вариант `original-retry` (тот же скрипт плюс до 8
  повторов HTTP) запущен один раз и тоже упал на 4-м запросе: 503 держался дольше всех восьми повторов.
  Поэтому роль «до» в таблице играет `eager`: новый цикл со старой стратегией «всё в промпте».
- **Лимиты ключа определяют время**: по 16–32 повтора на прогон (HTTP 429 и 503), около 16 успешных
  запросов в минуту.

Полная серия:

```bash
.venv/bin/python -m bench.run --variants original,original-retry,eager,full --runs 5
.venv/bin/python -m bench.run --variants eager,full-nocompact,full --runs 5 --window 16000 --enforce-window
```

Окно 16k выбрано ниже наблюдаемого пика (18,7–22,2 тыс.), чтобы лимит действительно срабатывал. Таблица пишется
в `bench/results/<дата>.md`: медиана и разброс по прогонам, кешированные токены по данным сервера, число
сжатий по уровням, загрузки скиллов, повторы запросов.

Новые отчёты локальных прогонов по умолчанию исключены из Git. В репозитории сохраняются JSON и Markdown
отчётов, на которые ссылается этот README, включая неуспешный baseline. При публикации новой сопоставимой
серии добавьте явные исключения в `.gitignore` и обновите ссылки; исходные отчёты вручную не редактируются.

Для раздельной проверки механизмов доступны `eager-managed` (все схемы, но включены compaction и лимит
вывода) и `full-no-cap` (полный харнесс без лимита текста в промпте; лимит захвата subprocess остаётся).
Управляемые варианты явно фиксируют эти флаги, независимо от окружения. Новых результатов для этих
вариантов пока нет.

Каждая новая серия сохраняет SHA-256 исходников, безопасный снимок настроек, версии Python и зависимостей,
а в Docker — идентификаторы обоих образов. Исходники сверяются до и после каждого прогона: при изменении
серия останавливается, смешанный отчёт не публикуется. Локальная блокировка на ключ запрещает одновременные
серии для одного пользователя на одном хосте; поддерживается `--jobs 1`. Ключ в артефакты не записывается.

В [CI](.github/workflows/tests.yml) добавлены офлайн-тесты на Python 3.10, 3.12 и 3.14 и Docker selfcheck.
Матрица CI должна быть подтверждена запуском в GitHub; локальная проверка не заменяет её.

## Ответы на вопросы

### 1. Как сделать compaction и подгрузку скиллов, не инвалидируя prompt cache на каждом шаге?

Кеш работает по префиксу токенов: изменение в позиции k обнуляет всё после k. Шаблон чата обычно рендерит
`tools` и системный промпт в самом начале. Отсюда правила, которые здесь реализованы:

1. **Начало промпта статично.** Системный промпт есть чистая функция конфигурации: без времени, cwd, счётчиков.
   Порядок `tools` фиксирован, сериализация детерминирована.
2. **Всё динамическое приходит в хвост.** Тело скилла и схема инструмента являются результатами тулов
   (`load_skill`, `tool_search`). Массив `tools` в режиме `dispatch` не меняется за весь прогон, инструменты
   каталога вызываются через один постоянный диспетчер `use_tool`.
3. **История между сжатиями только дописывается.** Подсказки харнесса («ответ обрезан», «вызов повторяется»)
   добавляются новым сообщением или в конец свежего результата, старые сообщения не правятся.
4. **Размер ограничивается на входе, а не задним числом.** Вывод обрезается до попадания в историю. Скользящее
   окно и «очистка старых результатов» на каждом шаге сдвигали бы префикс каждый ход, поэтому их нет.
5. **Compaction редкий и с гистерезисом.** Срабатывает на 75% окна, оставляет 40–60% (в реальных прогонах
   под окном 16k: около 9 тыс. → 5,1–5,6 тыс. токенов, три сжатия за 39–47 ходов). Кеш перестраивается
   один раз на сжатие, а не на каждом шаге, и только для саммари и хвоста: `system` и текст задачи остаются
   общим префиксом.
6. **Запрос на саммари сам попадает в кеш.** Это уже отправленный префикс плюс одна инструкция, с тем же
   `tools` и `tool_choice="none"`. Дешёвый уровень (заглушки вместо старых выводов) выбирается до любых правок
   истории, поэтому он не портит префикс для запроса на саммари.
7. **То, что обязано пережить сжатие, пишет харнесс.** Список загруженных скиллов и найденных инструментов
   добавляется в саммари детерминированно.

Если нативные определения тулов всё же нужно менять: только дописывать в конец, не переставлять и не удалять,
подгружать пачками. Там, где сервер это умеет, лучше не убирать тулы из промпта, а маскировать их при
декодировании. Для провайдеров с явными точками кеширования (Anthropic `cache_control`) точки ставятся после
`tools` + `system` и на последнем сообщении.

Как это проверяется: `PrefixTracker` считает для каждого запроса долю, побайтно совпадающую с началом
предыдущего. Это верхняя граница попаданий в кеш, не зависящая от того, отдаёт ли сервер `cached_tokens`.
В реплее это 97% для `dispatch` и 87% для `append`.

### 2. Какие ошибки тулов отдавать модели, а какие перехватывать в харнессе?

Критерий: **может ли модель исправить это следующим действием?**

**Модели** (как результат тула в формате `ERROR [класс]: сообщение` + `Hint:`, без трейсбека харнесса):

| Класс | Что получает модель |
|---|---|
| Ненулевой код возврата, stderr | Код, stdout, stderr как обычный результат |
| `invalid_arguments` | Все проблемы сразу и JSON-схема инструмента |
| `unknown_tool`, `unknown_skill` | Ближайшие имена |
| `not_found` | Похожие файлы в каталоге |
| `no_match`, `ambiguous_match` (правка файла) | Ближайшая строка или число совпадений |
| `timeout` | Хвост вывода до остановки и совет запускать в фоне |
| `invalid_json` | Позиция ошибки разбора |
| `truncated_call` | «Вызов обрезан лимитом вывода, ничего не выполнено, делай частями» |
| `policy_denied` | Причина и указание не повторять |
| `execution_error` | Тип и текст исключения |

**Харнесс** (детерминированно, со счётчиком в `metrics.intercepted`):

| Ситуация | Действие |
|---|---|
| 429, 5xx, обрыв сети, битое тело ответа | Ретрай с backoff, учёт `Retry-After` |
| 401, 403, 404, прочие 400 | Немедленное завершение со статусом `llm_error` |
| Переполнение окна | Compaction и повтор, затем сжатие без хвоста, затем статус `context_overflow` |
| Ответ обрезан по `max_tokens` | Просьба продолжить (до 3 раз) |
| `content_filter` / неизвестная причина завершения | Статус отказа, инструменты из ответа не выполняются |
| Лимит API-попыток / времени / `Ctrl+C` | `request_limit` / `time_limit` / `interrupted`, сохранение метрик |
| Пустой ответ | Напоминание (до 2 раз), а не завершение прогона |
| Однозначно исправимые аргументы | `"5"` → `5`, `"true"` → `true`, JSON в markdown-ограждении, двойное кодирование |
| Аргументы `use_tool` переданы плоско | Принимаются |
| Инструмент каталога вызван напрямую | Исполняется, а не возвращается «unknown tool» |
| Слишком большой вывод | Ограниченный захват процесса, затем обрезка для промпта и сохранение захваченного текста в файл |
| Зависший процесс, ожидание stdin, пейджер | Kill группы процессов, stdin закрыт, пейджеры отключены |
| Один и тот же вызов подряд | Предупреждение на 3-м, остановка со статусом `stuck` на 6-м |
| Невалидные аргументы в истории | В историю пишется валидный JSON, чтобы её можно было отправить снова |
| Имя переменной похоже на секрет | Значение скрывается |

Третья категория: то, что не может исправить никто (неверный ключ, неверная модель). Здесь нужны быстрый
отказ и понятный статус, а не ретраи и не попытки объяснить это модели.

## Ограничения

- Реальных прогонов мало: один-два на вариант, одна модель. Статистических выводов из них делать нельзя.
- Задача оказалась лёгкой для модели (12/12 почти везде), поэтому по успешности варианты различает только
  жёсткое окно.
- Вне Docker песочницы нет: `bash` исполняется с правами пользователя, ключ убран только из окружения команд,
  а `.env` на диске читается. В Docker у команд агента остаётся сеть.
- Оценка токенов приблизительная (символы на токен, калибровка по `usage`); точного токенайзера нет.
- Реплей фиксирует траекторию, поэтому не отражает того, что реальная модель в разных режимах ведёт себя
  по-разному.
- Саммари пишет та же модель; на слабых моделях качество сжатия нужно смотреть отдельно.
